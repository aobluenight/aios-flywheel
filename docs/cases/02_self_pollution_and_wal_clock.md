# 判例 02 · 监控器污染自己盯的东西 + WAL 时钟骗局（json_metric 的由来）

> 一案两坑，都发生在给流水线装"增量体检"的第一天。脱敏自真实产线。

## 坑 A · 基线写回被监控文件

第一版增量判定把"上轮指标值"直接写回被监控的 state 文件。副作用：`mtime` 被 touch 成"刚刚"。下一轮体检看到"0.1h 前刚写过"，判定活着——**但那条流水线其实已经死了半天**。监控器对被监控对象做任何写操作，都会伪造被监控对象的心跳。

**纪律：基线必须存独立文件（`.flywheel_baseline.json` 之类），与被监控 state 物理分离。**

## 坑 B · SQLite 主文件的 mtime 撒谎

给一个 WAL 模式的 SQLite 库装"新鲜度体检"，主库文件 mtime 长时间不动，被误判"两小时没写入、停转"。真相：WAL 模式下写入先进 `-wal` 文件，主库要等 checkpoint 周期才更新——**主库 mtime 滞后是正常的，不是死亡信号**。

**纪律：判定 WAL 库新鲜度，取主库与 `-wal` 的最小龄。**

## 沉淀

两坑共同通用化为 `json_metric`（增量判定，独立基线）与 `state_freshness` 的 `wal: true` 选项（最小龄判定）。空转判定一并内化：指标零增量 + 流程在跑 = idle（磨还在转，料没进来）——这是另一场真实事故（流水线 rc=0 但候选清单吃光、零新增，空转数日）的检测逻辑。

## 对应检查器

`ext/checkers.py::JsonMetric` / `StateFreshness`
